## Journal / me-wiki
- [ ] **Journal self-evolves into a "me-wiki"** — entity pages for the things she talks about (concepts, places, projects, symptoms, foods — not just people), definitions compiled from every reference, entries clickable into the wiki. Direction + architecture agreed 2026-07-13. Key realization: **the wiki engine already exists for one entity type** — `routes/entities.py` (index + backlinks over `people/*.md`, journal, THREADS/WORRIES), the `[[ref]]`/`tags:`/`aliases:` checked contract, the person-summary agent ("LLM compiles all references into a page"), PeoplePage/PersonPage. The me-wiki is that system with the "person" constraint removed — a generalization, not a greenfield build. Three load-bearing decisions:
  - **Never let an LLM write links into journal prose. Link at render time.** Entries stay untouched; the frontend linkifies by matching entry text against the entity index's names + aliases (Obsidian's "unlinked mentions"). Clickability lands across the whole archive retroactively, self-heals as the index grows, and the wiki can never corrupt an entry. LLM value-add is tags/metadata *beside* the entry (sidecar field on the stream-card, or a separate tags collection), never edits inside it — same write-safety doctrine as conversational capture above.
  - **The "self-evolving" loop goes through the existing approvals flow.** "Term X crossed N mentions → propose entity `x` with these aliases + draft definition" is exactly a pending-change: nightly pass (or Keeper) proposes → ApprovalsHost queue → tap yes → index grows. Definitions are *derived* content (person-summary-style), safe for an agent to regenerate wholesale — but keep an owner-notes section that never gets clobbered.
  - **This is the trigger for the parser-convergence todo below.** Generalizing entities *is* the "future SQLite migration of `entities.py`" moment that entry has been waiting for: make `entities.py` the one canonical parser/index, frontend consumes only its API, Rust tool shares the grammar. Don't add a fourth parser for concept pages.
  - **Slices, in order:** (1) render-time linkification — journal render matches known entity names/aliases from the existing index, click → entity page listing every reference; no LLM, no writes, weekend-sized, and the whole thing suddenly feels like a wiki. (2) Generalize the entity type — vault holds concept/place/project pages, probably just a `type:` in frontmatter. (3) The proposal loop — nightly pass over new cards proposes tags + new entities → approvals queue. (4) The definition compiler — person-summary generalized to any entity. Slice 1 pays off alone; each later slice enriches without rework.

Do it deliberately (it touches the live session server), not casually.
