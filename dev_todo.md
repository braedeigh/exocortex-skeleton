## Journal / me-wiki
- [ ] **Journal self-evolves into a "me-wiki"** — entity pages for the things she talks about (concepts, places, projects, symptoms, foods — not just people), definitions compiled from every reference, entries clickable into the wiki. Direction + architecture agreed 2026-07-13. Key realization: **the wiki engine already exists for one entity type** — `routes/entities.py` (index + backlinks over `people/*.md`, journal, THREADS/WORRIES), the `[[ref]]`/`tags:`/`aliases:` checked contract, the person-summary agent ("LLM compiles all references into a page"), PeoplePage/PersonPage. The me-wiki is that system with the "person" constraint removed — a generalization, not a greenfield build. Three load-bearing decisions:
  - **Never let an LLM write links into journal prose. Link at render time.** Entries stay untouched; the frontend linkifies by matching entry text against the entity index's names + aliases (Obsidian's "unlinked mentions"). Clickability lands across the whole archive retroactively, self-heals as the index grows, and the wiki can never corrupt an entry. LLM value-add is tags/metadata *beside* the entry (sidecar field on the stream-card, or a separate tags collection), never edits inside it — same write-safety doctrine as conversational capture above.
  - **The "self-evolving" loop goes through the existing approvals flow.** "Term X crossed N mentions → propose entity `x` with these aliases + draft definition" is exactly a pending-change: nightly pass (or Keeper) proposes → ApprovalsHost queue → tap yes → index grows. Definitions are *derived* content (person-summary-style), safe for an agent to regenerate wholesale — but keep an owner-notes section that never gets clobbered.
  - **This is the trigger for the parser-convergence todo below.** Generalizing entities *is* the "future SQLite migration of `entities.py`" moment that entry has been waiting for: make `entities.py` the one canonical parser/index, frontend consumes only its API, Rust tool shares the grammar. Don't add a fourth parser for concept pages.
  - **Slices, in order:** (1) render-time linkification — journal render matches known entity names/aliases from the existing index, click → entity page listing every reference; no LLM, no writes, weekend-sized, and the whole thing suddenly feels like a wiki. (2) Generalize the entity type — vault holds concept/place/project pages, probably just a `type:` in frontmatter. (3) The proposal loop — nightly pass over new cards proposes tags + new entities → approvals queue. (4) The definition compiler — person-summary generalized to any entity. Slice 1 pays off alone; each later slice enriches without rework.

## Dev workflow
- [ ] **Conversational capture → safe structured write to the build queue.** Goal: while journaling (Keeper) or in any persona session, name a build task/idea out loud and have the agent capture it into the backlog — *without* letting the LLM free-edit files (no unrecoverable mistakes). Architecture decided 2026-06-23:
  - **Safety lives in a constrained write path, not in prose.** The agent never edits the file; it calls *one narrow operation* — `add_todo(text, theme, source?)`, a small script or Flask endpoint — that validates the fields and appends atomically via `store.py`. The model fills slots; code does the write.
  - **Source of truth = a JSON in `personal/data`** (auto-committed hourly by `git_backup.sh`); `dev_todo.md` becomes a *generated, read-only view* of that JSON. Why: `dev_todo.md` lives in skeleton, which the cron only *pushes*, not auto-commits → direct edits have no backup. Moving the truth into the personal vault fixes recoverability. (Mirrors the existing "send to ideas" → `IDEAS.md` append flow.)
  - **Five safety layers:** append-only (never rewrite/delete) + schema validation + *you-confirm-before-it-lands* (a pending step / confirm tap = the "no irreversible mistake" guarantee) + `store.py` atomic writes + git history.
  - **Package the capability as a `context: fork` skill** (isolated subagent, fixed prompt, can't see/touch other files) — first real use of the existing "fork subagent skill" todo. CLAUDE.md/skill says *when*; the script/endpoint is the safe *what*.
  - **Flow:** journal naturally → task surfaces → agent proposes structured `{text, theme}` → you confirm → runs the one command → appends to JSON → md regenerates.
  - **Smallest shippable slice:** just the `add_todo` script + confirm (no fork, no pending queue) — ~1 hr. **Build after the job settles** (post-July fallow work, not pre-start). Also a dogfood of the product's core conversational-capture thesis.
- [ ] **Converge the people-file parser — one source, not three (or four).** The people/entities format (`- [[YYYY-MM-DD]] (note)` refs + `tags:`/`aliases:` frontmatter) is now parsed by **multiple independent implementations**: `routes/entities.py` (Python, the authoritative DB view), the new `tools/people/` Rust validator+writer, and hand-rolled JS in `templates/journal.html` + `templates/keeper.html` (frontmatter/markdown rendering). The Rust tool added real resilience (turned the format from a silent convention into a checked contract — its first run caught 15 references the DB had been dropping, now fixed, 2026-07-04). **But** its tests lock it to a *copy* of `entities.py`'s `_REF_RE`, not to the Python source — so if that regex ever changes, the parsers drift silently and the validator blesses files the DB then drops. Net: we traded a *loud, active* brittleness (file drift) for a *quiet, latent* one (parser-sync drift). Good trade, not free. **Resilient end-state:** one canonical parser everything else calls — e.g. have the Rust tool shell out to / share a spec with `entities.py`, or (cleaner long-term) make `entities.py` the single parser and expose it, with the frontend consuming only its API (mostly already true) and the Rust tool importing the same grammar from one shared definition. Latent + low-frequency — **horizon work, not urgent.** Belongs with any future SQLite migration of `entities.py` (the natural moment to collapse parsers). Judged by Terra 2026-07-04 as the one real cut in the validator build.
