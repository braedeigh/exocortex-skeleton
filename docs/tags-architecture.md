# Tags & the wiki-pond — design of record

One universal, namespaced tags table in `exo.db`, a wiki that reads it, and the
pond's drawing generalized to every tagged family. This doc is the contract:
the schema, the subject address scheme, the API shapes, and who writes what.
If a detail here and the code disagree, fix one of them — never let them drift.

## Why

The tagging pattern existed three times, each invented separately: `card_tags`
(free strings mixing people and thread slugs), `todo_fronts` (fronts only,
FK-enforced), and `topics[].fronts` inside the `research` doc blob. Every new
surface that wanted tagging would have minted a fourth dialect. This replaces
the pattern with one table any subject can use, and a wiki view over it.

## The `tags` table (schema v12)

```sql
CREATE TABLE tags (
  subject TEXT NOT NULL,   -- universal address, see below
  ns      TEXT NOT NULL,   -- 'front' | 'topic' | 'thread' | 'person' | any future structure
  tag     TEXT NOT NULL,
  source  TEXT NOT NULL DEFAULT 'manual'
          CHECK (source IN ('manual', 'derived', 'cricket')),
  created TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now')),
  PRIMARY KEY (subject, ns, tag)
);
CREATE INDEX tags_by_tag     ON tags (ns, tag);
CREATE INDEX tags_by_subject ON tags (subject);
```

- `ns` is what makes "other structures I may assign" free: a new namespace is
  a new `ns` value, zero schema changes. The UI groups its rail by `ns`.
- `source` keeps taxonomies sweepable: `derived` rows may be regenerated by
  re-running the backfill at any time; `manual` rows are the owner's hand and
  are never bulk-deleted; `cricket` rows came through a propose queue.
- The old junctions (`card_tags`, `todo_fronts`) STAY — the pond and todos
  still read them. The backfill mirrors them into `tags` with proper
  namespaces; new tagging writes go to `tags` only.

## Subject addresses

`<family>:<local id>` — the family prefix is what a tag page groups by.

| family    | address                          | local id source                    |
|-----------|----------------------------------|------------------------------------|
| `card`    | `card:2026-08-14.0930`           | cards.id                           |
| `todo`    | `todo:<id>`                      | todos.id                           |
| `entry`   | `entry:2026-07-06.2259`          | research.json entries[].id         |
| `topic`   | `topic:gut-microbiome`           | research.json topics[].id          |
| `thread`  | `thread:long-covid`              | Threads/<slug>.md                  |
| `person`  | `person:ezra`                    | people/<slug>.md                   |
| `note`    | `note:hair_care.md`              | *.md in EXOCORTEX_RESEARCH_DIR     |
| `file`    | `file:skeleton/routes/health.py` | files.repo + '/' + files.path      |
| `doc`     | `doc:buy_list#<item id>`         | item inside a docs-blob collection |

Validation at the write door: subject must match `^[a-z]+:.+`; `ns` and `tag`
must be non-empty slugs (`[a-z0-9][a-z0-9-_.]*`, lowercased on the way in).

## API — routes/tags.py

- `GET  /api/tags` → `{"namespaces": [{"ns", "tags": [{"tag", "count"}]}]}`
- `GET  /api/tags/for?subject=<subject>` → `{"subject", "tags": [{"ns","tag","source"}]}`
  (query param, not path — subjects contain slashes)
- `GET  /api/tags/tag/<ns>/<tag>` → `{"ns","tag","subjects": [{"subject","family"}]}`
- `POST /api/tags/add`    `{"subject","ns","tag"}` → the subject's tags (source='manual')
- `POST /api/tags/remove` `{"subject","ns","tag"}` → the subject's tags

Writes use `sqlstore.open_db()` inside `begin_immediate`; reads may use the
same door (tiny table). No JSON mirror — `tags` is a typed table like
`habits`, not a docs collection.

## Backfill — scripts/backfill_tags.py

Idempotent (`INSERT OR IGNORE`, all rows `source='derived'`), re-runnable any
time; `--dry-run` prints per-source counts without writing. Sources:

1. `card_tags` → `card:<id>`, ns classified the way routes/pond.py already
   classifies: people/<tag>.md → `person`; Threads/<tag>.md → `thread`;
   fronts.json id → `front`; else `topic`.
2. `todo_fronts` → `todo:<id>`, ns=`front`.
3. `research` blob: topic fronts → `topic:<id>` ns=`front`; entry topics →
   `entry:<id>` ns=`topic`; entry fronts = union of its topics' fronts.
4. Thread frontmatter: `thread:<slug>` ns=`front` (fronts:) + ns=`person` (people:).
5. `files` × the rules file `EXOCORTEX_DATA_DIR/tag_rules.json`:
   `{"rules": [{"repo", "prefix", "tags": [{"ns","tag"}]}]}` — every rule whose
   `prefix` prefixes the path applies (union, not longest-match). The rules
   file is install-specific and lives in the data dir, never in this repo.

## Wiki-pond — GET /api/wiki/pond (routes/wiki.py)

`?days=<n, default 45>&end=<YYYY-MM-DD, default today>`. Read-only, `mode=ro`
+ `query_only` (same belt-and-braces as routes/pond.py). Returns:

```
{"start", "end",
 "rows": [{"id": <subject>, "family": "journal"|"research"|"build"|"todo",
           "day", "ts", "title", "body", "tags": [{"ns","tag"}]}],
 "rail": [{"ns", "tags": [{"tag", "count", "span"}]}]}
```

- journal → cards in window (body capped like pond.py); research → research
  entries by created; build → commits by authored_at, tags INHERITED as the
  union of their files' tags (commit_files → file_paths → tags); todo → todos
  placed on finished_on, else created.
- `rail` counts only subjects present in the window; `span` = distinct days,
  same ranking philosophy as /api/pond/threads.

## Wiki-pond UI — frontend/src/features/wikipond/

Route `/wiki/pond` (file route `wiki_.pond.tsx`), linked from WikiHome. The
pond's grammar, generalized: day columns left→right; four family lanes down
each column; the rail grouped by namespace; lighting a tag is EMPHASIS, NOT A
FILTER (everything else stays drawn, dimmed); tap opens the full item with
its tag chips, editable through /api/tags/add|remove. Words mode follows the
pond's own precedent — journal + research lanes only, the prose-less lanes
switch off rather than pretending. Layout arithmetic lives in
`wikiPondMath.ts`, pure and tested, importing from `../pond/pondMath` where
shapes genuinely match.
